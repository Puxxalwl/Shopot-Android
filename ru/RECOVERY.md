# Восстановление аккаунта (ядро 2.6.0)

**[English](../docs/RECOVERY.md)** | Русский

Stille поддерживает **минимальный recovery-пакет**, чтобы новое устройство
могло продолжить использовать ту же криптографическую личность. Это
принципиально *не* синхронизация аккаунта: история сообщений, черновики и
файлы никогда не покидают устройство.

Recovery-блоб **принадлежит ядру** (`CREATE_RECOVERY_BACKUP` /
`RESTORE_RECOVERY_BACKUP`, API 2.6.0 — `CORE-API.md` §4.10). Клиент не
парсит, не перешифровывает и не выводит ключи для блоба: он проводит
unlock-церемонию и хранит запечатанный пакет в собственном облаке
пользователя.

## Что сохраняется

В Google Drive (скрытая область `appDataFolder`) хранятся ровно два
непрозрачных файла:

```text
appDataFolder/stille-recovery-v1.bin   — запечатанный ядром recovery-блоб
appDataFolder/stille-recovery-v1.meta  — публичный sidecar
```

Блоб создаёт ядро: ChaCha20-Poly1305 с ключом, выведенным (HKDF-SHA256)
из 32-байтового unlock-секрета. Внутри — seed личности, профиль, контакты
с маршрутами и блок-лист — всё, чтобы продолжить общение с теми же
людьми. **Истории сообщений внутри нет**; размер ограничен 92 786 байт
(`Limits.RECOVERY_BLOB`).

Sidecar — публичные метаданные, не секрет (CLIENT_RULES.md §4.2):

```text
magic      "STME"
version    1
key_source 1 = passkey PRF | 2 = код восстановления
prf_salt   32 случайных байта (только для passkey)
created_ms дата загрузки
api_version например "2.6.0"
```

## Unlock-секрет

Два источника (CLIENT_RULES.md §4.1), оба 32 байта, оба нигде не
хранятся:

1. **Passkey PRF** (основной). WebAuthn-passkey, синхронизируемый с
   аккаунтом Google, создаётся один раз при включении вместе со
   случайным PRF-солью. Вычисление той же пары (passkey, соль) на любом
   устройстве даёт тот же секрет. RP id `stille.app`.
2. **Код восстановления** (обязательный fallback). Если создание passkey или
   PRF недоступны (в том числе без привязки домена), пользователю один раз
   показываются 32 случайных байта (64 hex-символа группами по 8). Код нигде
   не сохраняется. Отмена подтверждения не запускает запасной сценарий.

Для доступа к Google Диску используется платформенный тип токена `oauth2:` и
окно разрешения с привязкой к Activity. Сеть и запрос токена работают вне
главного потока; подтверждение ключа и результаты UI — в главном потоке.
Настройка Google OAuth и привязка домена остаются требованиями к релизу.

## Пользовательский сценарий

Включение на старом устройстве (Настройки → Восстановление аккаунта):

```text
Включить восстановление
→ создать passkey (или получить код)
→ CREATE_RECOVERY_BACKUP(unlock_secret)
→ загрузить блоб + sidecar в Drive
```

Периодичность: повторить сценарий («Обновить backup») после изменений,
затрагивающих профиль (имя, аватар, контакты, маршруты, блок-лист).
Загрузка заменяет файлы на месте (PATCH), поэтому неудачная попытка не
уничтожает последнюю рабочую копию.

Восстановление на новом устройстве (экран приветствия → Восстановить
аккаунт):

```text
запустить ядро в recovery-режиме (serve без seed)
→ выбрать аккаунт Google
→ подтвердить passkey / ввести код
→ RESTORE_RECOVERY_BACKUP(blob, unlock_secret)
→ тот же аккаунт, пустая история
```

Демон стартует **без профиля** (`StilleService.startRecovery`): локальный
seed не создаётся, `GET_IDENTITY` отвечает `NOT_INITIALIZED`, UDS API
ждёт метод 42. Восстановление применяется только к пустому профилю
(`ALREADY_PROVISIONED` в противном случае — живой профиль никогда не
перезаписывается). Неверный секрет или повреждённый блоб дают
`BAD_RECOVERY` без побочных эффектов. При успехе личность подменяется на
месте, профиль (имя, аватар, контакты, маршруты) перезагружается, сеть
поднимается сама. Отмена диалога останавливает неподготовленный демон.

## Свойства безопасности

- Google хранит только запечатанный блоб; ключ не покидает
  аутентификатор устройства или руки пользователя.
- Клиент никогда не логирует, не парсит и не сохраняет unlock-секрет и
  блоб.
- Ядро перечитывает seed с диска при запечатывании; если файл seed
  исчез — пакет создать нельзя (`NOT_INITIALIZED`).
- Сам файл seed не передаётся; его восстанавливает ядро через
  собственный запечатанный путь.

## Требования к релизу

- OAuth-скоп `drive.appdata` требует верификации Google для
  production-сборок.
- RP id `stille.app` должен быть связан через Digital Asset Links до
  релиза, иначе passkey-церемония не заработает.
- Поддержка PRF зависит от платформенного аутентификатора; fallback на
  код восстановления должен оставаться доступным.
